# ADR-008: Java 25 LTS as the language baseline

Status: accepted (2026-08-21). **Supersedes [ADR-002](002-java-21.md).**

> The Java 25 decision remains authoritative. Its Gradle/Foojay commands and
> provisioning details are historical evidence only: [ADR-009](009-bazel-build.md)
> made this repository Bazel-only. Bazel's pinned remote JDK 25 is the build
> toolchain; native packaging separately requires a local JDK 25.

## Context

ADR-002 fixed the baseline at Java 21 LTS and said to revisit "when the next
LTS (25) has been GA long enough that a bundled-runtime bump costs nothing."
That condition is met, and the timing argument is stronger than mere
availability:

- **Java 25 is the current LTS.** Choosing 21 today means shipping a tool on
  the previous LTS from its first release, and inheriting a second migration
  later.
- **The project is at Phase 0.** Fifteen modules exist but almost no product
  code does — roughly a hundred tests, spikes, generators, and a window
  shell. A language baseline is cheapest to move exactly now: there is no
  large body of code to re-verify, no released artifact whose runtime
  contract changes underneath users, and no downstream consumer to coordinate
  with. Every phase we defer this makes the same change more expensive.
- **The alternative is doing it later, across a much larger codebase.** The
  cost of the move does not shrink over time; the code it has to survive
  grows through Phases 1–10.

Feasibility was verified before this ADR was written, in a scratch clone
setting `JavaLanguageVersion.of(25)`: `./gradlew check` passes (103 tests,
class-file major version 69), the app-window smoke run passes, all four
Phase 0 spikes pass, and the JMH benchmarks still compile. No source change
was required — the move is a toolchain change, not a migration.

The one behavioral difference observed is native-access warnings (see
Consequences).

## Decision

Target **Java 25 LTS** exactly. The current toolchain is pinned by Bazel under
ADR-009, so ordinary builds do not need a preinstalled JDK. `jpackage` is the
host-specific exception and requires a local JDK 25.

**Preview features remain forbidden.** This constraint is carried forward
from ADR-002 unchanged and is still binding: nothing in this repository may
require `--enable-preview`, and no incubator module may be depended on.
Raising the baseline widens the set of *final* features available; it does
not open the preview gate.

Everything ADR-002 relied on stays in force — records, sealed interfaces with
pattern-matching switch, virtual threads for blocking capture/enrichment
work, `java.awt.desktop` macOS integration, `ProcessHandle`.

## What newly becomes available (final in 25, verified non-preview)

- **Scoped Values** (JEP 506, final in 25). An immutable alternative to
  `ThreadLocal`, but **not the carrier for per-session diagnostic context**,
  despite looking like exactly that. Measured on this JDK: inside
  `ScopedValue.where(...).run(...)`, a child `Thread.ofVirtual().start(...)`
  and a task submitted to `newVirtualThreadPerTaskExecutor()` both reported
  `isBound() == false`, while `InheritableThreadLocal` did propagate.
  Bindings follow a single call stack, or cross threads only via
  `StructuredTaskScope.fork` — which is preview, and therefore banned. The
  threading model of plan section 19.2 is long-lived executors joined by
  bounded queues, so context crosses exactly the handoffs Scoped Values do
  not reach. Usable only within one single-threaded call stack (a headless
  import run, one query). Revisit when Structured Concurrency finalizes.
- **Flexible Constructor Bodies** (JEP 513, final in 25). Statements may
  precede `this()`/`super()`, so validation and argument normalization can
  happen before delegation instead of in static helper methods. Directly
  useful for the large population of validating records and value carriers.
- **Module Import Declarations** (JEP 511, final in 25). `import module M;`
  imports a module's exported packages. Available; adopting it is a style
  decision this ADR does not make.
- **Compact Source Files and Instance Main Methods** (JEP 512, final in 25).
  Relevant only to scratch and spike code, if at all; the shipped modules are
  ordinary classes.

**Structured Concurrency is still a preview API in 25** (JEP 505, fifth
preview) and is therefore **off-limits**. This is worth stating explicitly
because the plan's threading model (section 19.2 — a fan-out of blocking
capture, enrichment, and external-process tasks) is exactly its intended
consumer, and it is the one feature a reader would reasonably assume this
upgrade unlocks. It does not. Task fan-out continues to use the virtual-thread
executor and plain `Future` composition until Structured Concurrency
finalizes, at which point this ADR is the thing to amend.

Runtime-side, JDK 25 also graduates compact object headers from experimental
to a product feature. It was measured against this project and **not adopted**:
the benefit depends entirely on the shape of the records involved — a
`record(int, int)` shrank 24 → 16 bytes, while a `record(long, int, long)`
stayed at 32 because 8-byte alignment absorbed the smaller header — and the
data structures that dominate this project's memory are primitive arrays,
which have no per-object header to shrink. It should be re-evaluated once
Phase 3 defines the real domain records. docs/performance.md is the authority
on the measured figures and on the JDK each was taken under.

## Consequences

- **Contributors and CI use Bazel's pinned Java 25 toolchain.** The local
  JDK is ignored by ordinary builds. Native packaging is different: it uses
  the host's `jpackage` and rejects a version other than 25.
- **Native-access declarations are now required.** JDK 24+ warns when code in
  an unnamed module calls restricted methods such as `System::load`. Two
  load-bearing dependencies do exactly that: **FlatLaf** (macOS window
  decorations, ADR-001) and **sqlite-jdbc** (the per-session database,
  ADR-005). Neither can be dropped. The build therefore passes
  `--enable-native-access=ALL-UNNAMED` to every JVM it forks — test workers,
  `:app:run` and its start scripts, the spike tasks, and the JMH benchmark
  JVMs. This is currently only a warning, but running without the grant under
  `--illegal-native-access=deny` already makes sqlite-jdbc throw
  `SQLException: Error opening connection` rather than merely log, which is
  what a future JDK makes the default. The flag is a correctness requirement
  with a deadline, not cosmetic noise.
  Anyone launching the app or a spike with their own `java` command must pass
  it too — see docs/troubleshooting.md.
- **Phase 9 packaging bundles a 25 runtime.** `jpackage` produces the app
  image from the JDK 25 that builds it; the shipped app still depends on no
  system-installed JVM, and end users see no version requirement at all.
- **The floor rises for anyone consuming this repo's artifacts.** Not a
  concern today (the product is a packaged desktop app, not a library), but
  it is the reason to keep the baseline decision in an ADR rather than in a
  build file.
- ADR-002 stays in the tree as history, marked superseded. Its reasoning is
  still the reasoning; only the version moved.
- `docs/product-plan.md` is a verbatim reproduction of the approved plan and
  still says "Java 21 LTS". It is not rewritten; its ADR-002 section carries
  a pointer to this ADR, and this file wins on the baseline question.

## Revisit when

- **Structured Concurrency finalizes** (expected in a future release) — that
  is a concrete feature with a named consumer in plan section 19, and worth
  amending this ADR for.
- **The next LTS after 25 ships and has been GA long enough** that a
  bundled-runtime bump is free. The Phase-0 argument above will not apply
  then; expect the move to cost real verification work, and budget it.
- **A JDK makes native access mandatory rather than advisory.** The flag is
  already in place, but that release is the point to confirm FlatLaf and
  sqlite-jdbc still work under enforcement rather than assume it.

## Findings that constrain later phases

Measured on Corretto 25.0.1 during this upgrade. Recorded here because each
one contradicts something a later phase would otherwise assume.

- **`MemorySegment` removes the 2 GB mapping cap** (FFM, final since 22).
  Mappings of 8, 32, 128 and 512 GiB all succeeded, where `MappedByteBuffer`
  is hard-capped at `Integer.MAX_VALUE` bytes. Plan section 13.2 requires
  "segmenting when mappings become too large" — the *size* half of that
  rationale is obsolete on this baseline. Phase 5/7 should segment only for
  reasons that survive (incremental rebuild, index versioning), not for the
  2 GB limit. Caveat: a sequential sweep of a mapped segment measured ~1.3x
  slower than a heap `int[]`, while random-access BFS was a dead heat, so the
  choice is not free for scan-heavy paths.
- **The heap-array CSR indexes are already a Tier 3 scale risk.** The action
  forward+reverse pair alone is ~840 MiB at Tier 3 (`long[5,000,001]` offsets
  + `int[100,000,000]` targets, doubled) — about 21% of plan section 20.2's
  entire 4 GB budget, before any target-graph index exists. This is
  independent of the Java version and is the strongest argument for the
  memory-mapped index files of plan 13.2.
- **grpc-netty self-disables `sun.misc.Unsafe` on Java 25+**
  (`PlatformDependent.hasUnsafe() == false`). Good for the deprecation risk,
  but it is a real behavior change on the Phase 2 BES receive path, and its
  throughput effect against objective 1 (100k events/sec) is unmeasured.
- **The Security Manager is permanently disabled** —
  `setSecurityManager` throws even when passed null. Plan section 22.4's
  untrusted-input requirements ("treat imported SQLite databases as
  untrusted", "never load native code from a session archive") can never be
  backstopped by a sandbox, so the Phase 9 archive/parser review must carry
  that weight in validation code alone.
- **Incubator modules compile silently.** `javac --release 25` accepted
  `import jdk.incubator.vector.*` with no error and no warning, failing only
  at runtime with `NoClassDefFoundError`. An accidental incubator dependency
  would pass `./gradlew check` and break in the packaged app, so the
  no-incubator rule above cannot rely on the compiler to enforce it.
- **`sun.misc.Unsafe` use cannot be made fail-fast.**
  `--sun-misc-unsafe-memory-access` accepts only `allow|warn|debug`; `error`
  makes the JVM refuse to start. protobuf-java 4.36.0 does use Unsafe when
  `UnsafeUtil` initializes, though 20,000 real BEP round-trips never
  triggered it. Unlike native access, this posture cannot be pre-verified.

  Phase 4 added a second user, and this one is not merely potential:
  `io.airlift.compress.zstd.UnsafeUtil` calls `Unsafe::objectFieldOffset` on
  every run that decompresses a compact execution log, and the JVM prints the
  terminal-deprecation warning to say so. It still works on Java 25 and is
  warned about rather than blocked.

  The exposure is bounded and the exit is known. Only the compact execution log
  is zstd-framed, only Bazel 7+ writes one, and the binary format needs no
  decompressor at all — so a JVM that removed Unsafe outright would cost the
  compact format and not the phase. The replacement is `zstd-jni`, which uses
  native code instead and would trade this warning for a per-platform binary
  matrix; that trade was declined when the dependency was chosen, and this note
  is what would reopen it.
