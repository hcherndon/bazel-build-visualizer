## CRITICAL

### C1 — `journal.force()` throws `IllegalStateException` out of `run()`'s finally, so the session is never finalized and its lock is never released

**Confidence: contested, 2‑1.**
**Location:** `capture-bes/src/main/java/com/holtherndon/bazelviz/capture/live/LiveCapturePipeline.java:418`; secondary at `CaptureCoordinator.java:539` (`finishQuietly`).

**Defect.** `finish()` calls `journal.force()` unguarded. `JournalWriter.force()` begins with `ensureUsable()`, which throws `IllegalStateException` once `failed` is set. `finish()` declares only `IOException`/`SQLException`/`InterruptedException`; `run()` catches only `SQLException` and `InterruptedException`; `finishQuietly` catches only `IOException | SQLException` and `InterruptedException`. So the unchecked exception escapes `run()`'s `finally` and aborts every remaining cleanup statement.

**Failure scenario (reproduced end‑to‑end from `bbv run` against real Bazel 7.6.1 on a 20 MB disk image):** the journal write fails mid‑build with `IOException: No space left on device` while SQLite is still writable (WAL reuses its file in place; `BatchedInsert.flush()` is a no‑op at zero pending rows). `run()` line 255 calls `pipeline.finish()`, which throws at line 418; `finishQuietly` calls it a second time and throws the identical ISE, which escapes the finally. Observed on disk: `manifest.json` state `CAPTURING` (non‑terminal), `warnings: []`, `locks/session.lock` still present with a live pid, SQLite connection and journal fd leaked, `bbv` exited 3 through the unhandled‑exception path instead of returning a `CaptureResult`. Plan 21.2 requires "attempt to preserve already written data" and "mark the source incomplete"; phase2‑contracts §8 requires INCOMPLETE when "a journal write failed". Neither happens.

**Fix.** Skip `force()`/`flush()` when `journal.isFailed()` (or record the failure in the summary instead of throwing); make `finish()` idempotent so a second call cannot re‑run `persistStreamStates`, which today re‑emits every `STREAM_ABORTED`/`SEQUENCE_GAP` diagnostic. Independently, wrap `finishQuietly` in `catch (RuntimeException)` so no cleanup step can prevent `finalizeSession` and `session.close()` from running.

**Refutation.** 1 of 3 refuted. The dissenter's strongest argument: the *stated* consequences are not caused by this line. At the moment `finish()` throws, `terminal` is still `FAILED_TO_START`, which has no legal path from `CAPTURING`, so `finalizeSession` throws and swallows regardless — making `finishQuietly` catch `RuntimeException` leaves the manifest at `CAPTURING` and the §8 gap unfixed. That gap is H1, not this line. They also showed `JournalWriter.close()` skips `drainBuffer()`/`force()` when failed, so plan 21.2's preserve‑data clause loses zero bytes, and the failure is loud on three channels (Bazel exits 38, the Swing dialog shows the ISE message verbatim, `CliMain` prints the trace). **This dissent is about severity, not existence** — the two surviving refuters reproduced the escaping exception from a real `bbv run` and observed the leaked lock and leaked fds. Fix C1 and H1 together; neither alone restores §8.

### C2 — `finish()` blocks forever when the journal thread has already died and the receive queue is full

**Confidence: unanimous, 6‑0** (filed independently by the concurrency and session lenses; six refuters, none refuted).
**Location:** `LiveCapturePipeline.java:411`.

**Defect.** `finish()`'s first act is `receiveQueue.put(END_OF_STREAM)` — an unbounded wait. `runJournal` is the queue's only consumer, and it exits permanently on any `IOException | RuntimeException` from `journal.append`/`journal.flush` (line 266), signalling only `NORMALIZE_END` onward. Nothing ever drains `receiveQueue` again.

**Failure scenario.** A journal write fails mid‑build (disk full, plan 21.2). The capture is under backpressure — the designed steady state, which the class itself names ("The queue is full: this is the backpressure") — so `receiveQueue` is at its 4,096 capacity with a gRPC handler parked in `submit`'s `put`. `poll()` frees a slot, the parked producer immediately refills it, and the `append` that fails happens with the queue back at capacity. `CaptureCoordinator.run()` line 255 calls `pipeline.finish()`, which never returns. `run()`'s finally never executes: no `finalizeSession`, no `session.close()`, no `SessionDatabase.close()`, no journal close. In `bbv run` the CLI hangs indefinitely after Bazel exits (Ctrl‑C then takes ~30 s via `CancellationGuard`'s bounded wait, printing `RUN_TIMED_OUT`, and halts mid‑capture); in the UI the `bbv-capture` worker parks forever, `captureFinished` is never delivered, `active` is never cleared, and `isBusy()` stays true for the life of the app. On restart the session is `CAPTURING` with a lock held by a live hung process, so `SessionLock.inspect` reports it not breakable and `SessionManager.recover` throws `SessionLockedException`.

Reproduced three ways by three refuters, all with production configuration: a real ENOSPC on a 4 MB HFS RAM disk with `receiveQueueCapacity` 4096 and a **single** serial producer (matching gRPC's per‑stream `onNext` serialization); a read‑only raw directory forcing `AccessDeniedException` from `rotate()`; and a mid‑capture `chmod`. All three produced `finish() BLOCKED` with the stack top at `ArrayBlockingQueue.put(...) → LiveCapturePipeline.finish(LiveCapturePipeline.java:411)`.

**Fix.** Do not signal end‑of‑stream by an unbounded `put`. Either set a volatile `finishing` flag the journal loop polls on its 50 ms timeout, or use `receiveQueue.offer(END_OF_STREAM, timeout, unit)` and, on timeout or when the journal thread is no longer alive, drain the queue and account for the abandoned submissions as unjournaled (`received != journaled` already reports this honestly). `runJournal`'s exit path must drain `receiveQueue`, releasing parked submitters with `CaptureRejectedException`. Whichever is chosen, `finish()` must be safe to call when the journal thread is dead.

**Refutation.** 0 of 6 refuted. Strongest challenge raised: the collision of "journal fails" with "queue exactly at capacity" is an interleaving, not a guarantee — if no producer is parked, `put` succeeds and `finish()` correctly returns a summary carrying the failure. This did not survive: the single‑producer case is deterministic (`poll()` frees one slot, the lone parked producer refills it, the failing append happens at capacity), and sustained backpressure is the documented loaded state the code emits `CAPTURE_LAG` for. **Two corrections to the original evidence:** (a) the claim that "the `CancellationGuard`'s 30 s wait never completes" is false — `settled.await(waitMillis, …)` is bounded, so Ctrl‑C does terminate the CLI after ~30 s, leaving an unfinalized session rather than a permanent hang; (b) there is a second, independent route to the same wedge — `runStore` exits on `SQLException` without draining `normalizeQueue`, so the journal thread parks forever in `normalizeQueue.put` at line 255 once 16,384 frames accumulate, and `finish()` then hangs at `joinQuietly(journalThread)` (line 412). The `finally` at line 272 (`normalizeQueue.put(NORMALIZE_END)`) is the same untimed put and will hang the journal thread if the store thread has already failed. Fix all three puts.

Also noted: `PublishBuildEventService.publishLifecycleEvent` (line 186) does `journaled.await()` with no timeout, so a lifecycle handler whose submission was queued when the journal died parks forever too.

### C3 — `cancel()` is a silent no‑op until the process handle exists, so Ctrl‑C / Stop is dropped and the build launches anyway

**Confidence: unanimous, 9‑0** (filed independently by the concurrency, process, and CLI lenses; nine refuters, none refuted).
**Location:** `CaptureCoordinator.java:298‑302` (the dropped request) and `RunCommand.java:127` (the missing pre‑launch check).

**Defect.** `cancel(mode)` reads `running.get()` and returns silently when it is null. `running` is only populated at `CaptureCoordinator.java:251`, *after* `BazelLauncher.start()` has already spawned the process. No record of the request is kept. `CancellationGuard.wasCancelled()` has **zero callers anywhere in the repository**, so nothing between the guard's listener and `coordinator.run()` consults it.

**Failure scenario (CLI, the severe one).** `bbv run -- build //...`. `RunCommand.java:106` registers `guard.onCancelRequested(() -> coordinator.cancel(CANCEL))`, then runs `preflight()` — executable resolution (`VERSION_TIMEOUT` 90 s) plus `bazel help flags-as-proto` (`DEFAULT_TIMEOUT` 60 s; ~0.7 s warm, far longer while bazelisk downloads a toolchain), all with no terminal output at all. The user presses Ctrl‑C. The hook sets the flag, calls `cancel(CANCEL)` → `running` is null → returns, and prints `interrupted: asking Bazel to stop and finalizing the session…` — a statement that is false at the moment it is printed. The main thread is unaffected and proceeds to `coordinator.run()`, which creates a session and starts a real Bazel build. Measured twice against Bazel 9.2.0:

- Short build, SIGINT at t=3 s: stderr printed the stopping message; the build ran to completion; stdout reported `"state": "READY", "build": {"exitCode": 0, "succeeded": true}`. The user pressed Ctrl‑C and got a completed build.
- Build longer than 30 s, SIGINT at t=3 s: the build launched at ~t=13 s; at t=33 s the hook's `settled.await` expired, printed `the build did not stop within 30s`, and the JVM halted mid‑capture. **stdout was completely empty** (a `--json` consumer gets a zero‑byte document), the manifest was left at `"state": "CAPTURING"`, `checkpoints/` empty, `locks/session.lock` present, `session.sqlite-wal` un‑checkpointed. Exit 130. The orphaned Bazel client survived the halt (confirmed by `ps`).

`bbv run --help` states "Ctrl-C asks Bazel to stop and finalizes the session as cancelled, which leaves it inspectable." Neither half happens in this window.

**Failure scenario (UI).** `LaunchController.preflight` installs the coordinator into `active` synchronously *before* dispatching to the worker, and `MainWindow.startLaunch` sets `Phase.PREPARING`, which `CaptureStatusModel.withPhase` marks `cancellable = true`. All three stop buttons are live for the entire probe and every click reaches the silent return. A second, narrower window runs from `LaunchController.launch()`'s `captureStarted` post through `run()`'s prologue (session create, `SessionDatabase.open`, `MigrationRunner.migrate`, `JournalWriter.create`, `pipeline.start()`, `ConsoleCapture.open`) until line 251.

**Fix.** Make the request sticky: `AtomicReference<CancellationMode> pendingCancel`; `cancel()` stores the mode (highest rung wins) and applies it immediately if a process exists. `run()` must check it before `BazelLauncher.start` — abandoning the launch and finalizing the session as CANCELLED — and again immediately after `running.set(process)`. `RunCommand` must additionally test `guard.wasCancelled()` after `resolveConflicts` and before `coordinator.run()`. Preflight itself should abandon its probe subprocess when the guard is raised.

**Refutation.** 0 of 9 refuted. Strongest challenges, and why they did not land:

- *"The UI's PREPARING click cannot cause an unwanted build."* Correct, and this is a real correction to the filing: `planReady` opens a mandatory `APPLICATION_MODAL` `InstrumentationPlanDialog` and only launches on an explicit LAUNCH choice. So the UI's long PREPARING window costs the user three dead buttons with no feedback, not an unwanted build. **The CLI half carries the severity.**
- *"The probe is ~0.7 s, not 60 s."* True for a warm bazelisk; the 60/90 s figures are the code's own timeouts, and the window widens whenever bazelisk must download. Either way the window is silent on the terminal, which is exactly when a user reaches for Ctrl‑C.
- *"The session is recoverable, so the halt is bounded."* `SessionLock` is a pid + start‑time JSON record, not an OS lock, so it reads STALE after the process exits — the "lock held" framing in the original filing is wrong. But the lost stdout, the unfinalized `CAPTURING` manifest, and the orphaned client are not recovered by anything, and `SessionManager.recover` is wired only into `ImportCommand`'s `--resume` path, which matches candidates by source *file* path and can never match a capture session.
- *"Ctrl‑C also SIGINTs the probe subprocess, so preflight will fail."* It does not. `BazelCapabilityDetector.probeFlagsProto` catches `IOException | InterruptedException` and returns `Optional.empty()`; the probe degrades to `unprobed`, `isInstrumentable` returns true for an unprobed binary, and the build launches anyway — now uninstrumented as well as unwanted (see C4).

Related but separately fixable: M6 (the UI affordance).

### C4 — A capture that received zero events is finalized READY, reported "complete", and exits 0

**Confidence: unanimous on the core, 9‑0** (filed by the session, CLI, and UI lenses); **the planner‑gate half is contested, 2‑1**.
**Location:** `CaptureSummary.java:54` (`isComplete()`), `CaptureCoordinator.java:393` (`terminalStateFor`) and `:435` (`updateManifestCounts`), `RunCommand.java:233`/`:266`, `MainWindow.java:580`. Related planner gate: `InstrumentationPlan.java:74` (`canLaunch()`).

**Defect.** `isComplete()` is `failure.isEmpty() && received == journaled && journaled == normalized + nonEventEnvelopes && streams.stream().allMatch(...)`. Every clause is vacuously true at zero — `0 == 0`, `0 == 0 + 0`, and `allMatch` over an empty list. `terminalStateFor` falls through every guard to `READY`; `updateManifestCounts` unconditionally stamps the `BES_STREAM` source `Completeness.COMPLETE` with the note "0 stream(s), 0 event(s) received"; `RunCommand.report` prints `capture: complete`; `exitCodeFor` returns `ExitCode.OK`; `MainWindow.captureFinished` selects `Phase.DONE` ("Finished — build succeeded · capture complete · 0 events indexed"). Nothing anywhere asks whether a stream was ever opened.

**Four measured triggers.**

1. **`--keep-bes`** (`bbv run --keep-bes -- build --bes_backend=grpc://host:443 //...`). The planner takes `addBepFileFallback` and injects `--build_event_binary_file=<session>/raw/bep-fallback.bin` **instead of** a local BES backend, so the embedded server receives nothing. Bazel wrote 32,933 bytes of real BEP into that file; `bep_events` had 0 rows, the journal was 32 bytes (header only), the manifest listed **no source entry for the fallback file at all** plus `{"kind":"BES_STREAM","byteSize":0,"completeness":"COMPLETE"}`, and stdout reported `"state":"READY","complete":true`, exit 0.
2. **Bad user flag.** `bbv run -- build --definitely_not_a_flag //...` — Bazel exits 2 during option parsing before publishing anything. Measured: `"received": 0, "complete": true, "warnings": []`, exit 0.
3. **Bad line in `~/.bazelrc`.** Verified with `HOME=/tmp/fakehome` containing `common --bogus_flag_xyz=1`: exit 2, 0 events, `complete: true`, exit 0.
4. **Unprobed Bazel.** Both capability probes fail → every capability UNKNOWN → `AddedFlag.isApplied()` false → `applyTo` appends nothing → `effective == original`, no error, no mandatory conflict, `canLaunch()` true. The user's entire build runs with zero instrumentation and the empty session reports complete. `InstrumentationPlan.isPassThrough()` names this exact state and has zero callers.

A CI job doing `bbv run … && analyze` sees a green exit and archives an empty session claiming a COMPLETE BES capture source. Plan rule 26 forbids exactly this ("never claim completeness the sources do not support"), and `docs/implementation-status.md:246` offers `isComplete()` as the evidence for Phase 2 exit criterion 3 — a predicate that cannot fail for a capture that got nothing.

**Fix.** Three parts.
1. `CaptureSummary.isComplete()` must be false when no stream was ever seen and one was expected — or add an explicit `capturedAnything()` that `terminalStateFor` consults — so a zero‑stream capture finalizes INCOMPLETE with a discrepancy naming the reason.
2. `updateManifestCounts` must not write `Completeness.COMPLETE` for a `BES_STREAM` source with zero streams and zero bytes; `UNKNOWN`, or no entry at all, is the honest record.
3. In `InstrumentationPlanner`, add a plan **error** when `DataSource.BES_ENVELOPE` and `DataSource.BEP` are both non‑PLANNED (equivalently when `isPassThrough()` and no user‑supplied capture flag was detected), so `canLaunch()` is false. The planner already treats the analogous case correctly one branch up: a missing BES endpoint is an error, "not a silently uninstrumented build".

Additionally, the `--keep-bes` path needs the fallback file to be ingested or the resolution withdrawn — see completeness‑critic finding CC2, which is the same defect from the other end.

**Refutation.** 0 of 9 refuted on the core claim (session 3‑0, CLI 3‑0, UI 2‑1 — the UI dissenter's argument is below); the planner‑gate half survived 2‑1.

Strongest challenges: *the count is printed immediately next to the claim* (`events: 0 received, 0 journaled, 0 indexed` sits directly above `capture: complete`; the UI detail line reads "capture complete · 0 events indexed"), and for the unprobed trigger the plan dialog does render `· --bes_backend=… — not applied: this Bazel could not be probed` together with `Required: without it there is no capture.` before launch. Those mitigate the *human* reading and are why the UI vote went 2‑1. They do not touch the machine‑readable channels: `printPlan` is skipped entirely under `--quiet` or `--json` (`RunCommand.java:109`), so `bbv run --json` emits `"state":"READY"`, `"capture":{"complete":true,"received":0,"discrepancies":[]}`, `"injectedFlags":[]`, `"warnings":[]`, exit 0, with no signal at all — and the manifest's `Completeness.COMPLETE` is persisted, not merely printed.

One correction to the original filing: the `.bazelrc` trigger for the *unprobed* path is defused — both probes pass `--ignore_all_rc_files` and run from a scratch temp dir, so a bad rc line cannot break the probe. It can and does break the *build* (trigger 3 above), which reaches the same zero‑event outcome by a shorter route. The planner dissenter's argument was that `isComplete()` is faithful to its own documented contract ("no accepted event is silently dropped") and nothing was dropped; the answer is that `terminalStateFor` and `updateManifestCounts` treat that pipeline‑integrity predicate as an answer to "did the session capture what the plan promised", which it is not.

## HIGH

### H1 — `run()` initialises `terminal` to `FAILED_TO_START`, which is unreachable from `CAPTURING`, so any post‑launch failure leaves the session permanently non‑terminal

**Confidence: contested, 4‑2** (filed by the concurrency lens as MEDIUM and the session lens as HIGH; reported here at the higher severity).
**Location:** `CaptureCoordinator.java:203`.

**Defect.** `SessionState terminal = SessionState.FAILED_TO_START;` is set before the try and reassigned only at line 256 (success) or 263 (InterruptedException). `SessionState.allowedNext()` gives `PREFLIGHT → {CAPTURING, FAILED_TO_START}` and `CAPTURING → {BUILD_FINISHED, CANCELLED, INCOMPLETE, CORRUPT_PARTIAL}` — `FAILED_TO_START` has no other predecessor. The session moves to `CAPTURING` at line 247, before `ProcessBuilder.start()`, as §8 requires. Anything other than `InterruptedException` thrown between 247 and 256 reaches the finally with `terminal == FAILED_TO_START`, `ManagedSession.finalizeSession` finds no path, throws `IllegalStateException("no legal path from CAPTURING to FAILED_TO_START")`, and `CaptureCoordinator.finalizeSession` swallows it into a log line. The manifest stays `CAPTURING` forever. The `SQLException` branch at line 257 is broken the same way: it adds a warning and rethrows as `IOException` without reassigning `terminal`.

**Failure scenario.** Reproduced end‑to‑end against the real classes: preflight succeeds, the working directory is removed between preflight and launch, `BazelLauncher.start()` throws `IOException`. Result: `run() threw: the working directory does not exist`, leftover session at `state=CAPTURING`, persisted `manifest.json` with `"warnings": []`. `ProcessBuilder.start()` produces the same for `error=2` (bazel replaced), `error=13`, `error=24` (EMFILE), `error=12` (fork failure). A non‑TOCTOU trigger also exists and is more likely: `pipeline.finish()` at line 255 declares `throws IOException, SQLException, InterruptedException`, so a disk‑full at end of capture — the exact "process died, or a journal write failed" case §8 says must yield INCOMPLETE — lands here.

The state‑machine's refusal is already pinned by a passing test: `SessionStateTransitionTest` line 147, "Nothing can reach FAILED_TO_START once capture has begun."

**Fix.** Set `terminal = SessionState.INCOMPLETE` at the moment the session moves to `CAPTURING` (or derive the fallback from `session.state()` inside `finalizeSession`: `FAILED_TO_START` only while still NEW/PREFLIGHT, INCOMPLETE otherwise). Also persist the "could not be finalized cleanly" warning — today it is appended at line 414, *after* the `addWarning` loop at 406‑408 has already run, so it never reaches the manifest.

**Refutation.** 2 of 6 refuted. Their strongest argument: `SessionManager.recover(root, MARK_INCOMPLETE)` maps `terminalFor(CAPTURING) → INCOMPLETE`, which is a legal edge, and `SessionManagerTest.recoveringACapturingSessionAsIncompleteKeepsItInspectable` proves the whole repair path works with a persisted warning — so "permanently non‑terminal" is wrong, and the user is told the real cause through the exception channel (`bbv: the capture could not run: …`, or the Swing error dialog) rather than through the state label.

**Why this still stands.** `recover()` has exactly two production call sites, both in `BepImporter` on the file‑import resume path, and `findInterrupted()`'s only consumer is `ImportCommand.locateResumableSession`, which filters candidates to those whose manifest `sources[]` name the file being imported — a capture session's sources are `BES_STREAM`/`STDOUT`/`STDERR` and can never match. `MainWindow` constructs a `SessionManager` and never calls `findInterrupted`. There is no `bbv recover` subcommand. So the repair machinery exists, is tested, and is wired to nothing that can reach a capture session. Two smaller corrections from the refuters, both accepted: `ConsoleCapture.open` is at line 242, *before* the CAPTURING transition, so it is not a trigger; and warnings collected before finalization *are* persisted — only the meta‑warning is lost.

### H2 — The BEP‑file fallback silently overrides the user's own `--build_event_binary_file`

**Confidence: unanimous, 3‑0.**
**Location:** `InstrumentationPlanner.java:265` (`addBepFileFallback` signature) and `:277` (the unconditional append).

**Defect.** `addBepFileFallback` takes no `UserFlags` parameter and never consults one; it unconditionally appends `--build_event_binary_file=<session>/raw/bep-fallback.bin`. Its two siblings in the same file do the right thing — `addBesTimeout` guards with `if (userFlags.has(flagName)) return;`, `addBesBackend` emits a `ReplacedFlag` — so the omission is an oversight, not a policy. `PlanConflict.Kind.EXISTING_BEP_OUTPUT` is declared at `PlanConflict.java:46` for exactly this case and is **never constructed anywhere**.

**Failure scenario.** A CI build both uploads to a BES backend and writes a local BEP for a downstream step: `bbv run --keep-bes -- build --bes_backend=grpc://corp.example:443 --build_event_binary_file=/tmp/ci-events.bin //...`. Running the shipped classes produced:

```
canLaunch=true
effective=[…, --build_event_binary_file=/tmp/ci-events.bin,
              --build_event_binary_file=<session>/raw/bep-fallback.bin, …]
replaced=[]   conflicts=[]
```

`build_event_binary_file` is single‑valued (`allows_multiple=0` on all four measured Bazel versions, `docs/bazel-ground-truth.md:292`) and injected flags are appended last, so last‑wins: only the session copy is written. This breaks phase2‑contracts §6 verbatim — "User-supplied options win. Overriding one requires a `ReplacedFlag`… The type makes a silent override impossible" — and plan 8.4's "Existing files must not be overwritten without explicit policy". `replacedFlags` is empty.

**Fix.** Pass `UserFlags` into `addBepFileFallback`; when the user already set the flag, raise a mandatory `EXISTING_BEP_OUTPUT` conflict offering (a) redirect to the session file, recorded as a `ReplacedFlag` carrying the user's original argv, (b) keep theirs and read the file they named, (c) cancel. Do not append the session copy until one is chosen.

**Refutation.** 0 of 3 refuted. Strongest challenge: nothing is *destroyed* — Bazel never opens `/tmp/ci-events.bin`, so a pre‑existing file is left stale and untouched (which is worse for a re‑run workspace: the downstream step consumes last run's events as fresh) or, on a clean checkout, simply never created. Refuters also noted the trigger requires the user to hold both `--bes_backend` and `--build_event_binary_file` *and* to opt into `--keep-bes`, and that `printPlan` shows the duplicated flag in the `effective:` line by default — though not under `--quiet` or `--json`, and nothing labels it as an override. Two refuters proposed downgrading to MEDIUM on that basis; the contract violation is unambiguous either way. On the `--replace-bes` path the user's flag survives untouched, so this is specific to the keep‑BES branch.

### H3 — `finish()` on an interrupted thread skips the entire drain, and `close()` then interrupts the journal writer

**Confidence: contested, 2‑1.**
**Location:** `LiveCapturePipeline.java:410‑411` (interruptible `put`), `:528‑533` (`close()` interrupting both threads), reached from `CaptureCoordinator.java:539/548`.

**Defect.** `finish()`'s first blocking call is `receiveQueue.put(END_OF_STREAM)`. `ArrayBlockingQueue.put` uses `lock.lockInterruptibly()`, which throws **before touching the queue** — verified on this JDK: "put threw InterruptedException with an EMPTY queue; queue=0". So on a thread whose interrupt flag is set, `END_OF_STREAM` is never enqueued, `joinQuietly` never runs, and `persistStreamStates`/`events.flush()`/`writeCheckpoint()`/`journal.force()` are all skipped. `finishQuietly`'s finally then calls `pipeline.close()`, which interrupts `journalThread` — precisely what phase2‑contracts §4 forbids ("Never interrupt the journal-writer thread to cancel. FileChannel closes itself on interruption, so an interrupt truncates the capture") and what `JournalWriter`'s own javadoc (lines 50‑53) warns against.

**Failure scenario.** `captureWorker.shutdownNow()` in `MainWindow.dispose()` interrupts the thread inside `CaptureCoordinator.run()`; `process.await()` → `waitFor()` throws; the catch at line 260 re‑sets the flag; the whole finally runs interrupted. Up to 4,096 queued events are discarded unjournaled with no counter. Then `closeJournalQuietly` calls `journal.close()` → `drainBuffer()` → `channel.write` **on the same interrupted coordinator thread**, which `AbstractInterruptibleChannel.begin()` self‑closes: measured, all 20 staged 1 KiB frames lost, only the 32‑byte segment header on disk, `close() threw ClosedByInterruptException`. Those frames were **already acknowledged to Bazel** — `onJournaled` runs at line 250 immediately after `append` returns, before any flush. `close()` also does not join the threads, so `journal.close()` on the coordinator thread can run concurrently with the journal thread still inside `append`/`flush`, which `JournalWriter`'s javadoc declares a programming error.

**Fix.** Make `finish()` interrupt‑tolerant: save and clear the interrupt status for the duration of the drain and restore it before returning, or enqueue `END_OF_STREAM` uninterruptibly. In `close()`, join the threads with a bounded wait after interrupting, so the writer is never interrupted while the coordinator still intends to use its output. Independently — and this is the part the dissent makes load‑bearing — clear and restore the interrupt flag around `CaptureCoordinator.run()`'s entire finalization block.

**Refutation.** 1 of 3 refuted. The dissenter's strongest and partly correct argument: **the causal story in the filing is wrong.** A `FileChannel.write` issued by a thread whose flag is *already* set fails regardless of what happened to `journalThread` — `closeJournalQuietly` runs on the coordinator thread, so the staged buffer is lost whether or not line 529 exists. Conversely, `journalThread.interrupt()` can only reach a live journal thread when the caller is already interrupted, because every other route into `finishQuietly` reaches `close()` after `finish()` has joined both threads. So removing the interrupt, or making line 411 uninterruptible, preserves **zero** frames on its own; the only real hardening is the interrupt‑clear‑and‑restore in `CaptureCoordinator`. The dissenter also bounded the loss: `journalFlushInterval` is 500 ms, so at most one flush interval sits in the buffer, which is the same envelope `JournalWriter` documents for process death; and `JournalRecovery.recover` truncates to the last intact frame, so there is no corruption. Finally, the §4 rule they read as governing *cancellation* is not crossed by cancellation here — the UI Stop button and `CancellationGuard` both signal without interrupting.

**Verdict:** the defect is real, the harm is smaller than filed, and **the fix location moves** — put the interrupt guard in `CaptureCoordinator.run()`'s finally, not only in `LiveCapturePipeline`.

### H4 — Closing the main window destroys a running capture, blocks the EDT for up to 10 s, and interrupts the capture thread

**Confidence: contested, 7‑2** (filed by the concurrency, UI, and process lenses; nine refuters, two refuted).
**Location:** `MainWindow.java:197` (`discardPlan()`), `:199` (`captureWorker.shutdownNow()`), with `setDefaultCloseOperation(DISPOSE_ON_CLOSE)` at `:154`.

**Defect.** `dispose()` runs on the EDT and calls `launchController.discardPlan()` unconditionally. `discardPlan()` is `active.getAndSet(null)` + `coordinator.close()` with no `isBusy()` check, and `active` holds the *running* coordinator for the whole build (it is cleared only in `launch()`'s finally). `CaptureCoordinator.close()` → `BesServer.close()` → `server.shutdown()` then `server.awaitTermination(shutdownGrace)` — `BesServerConfig.defaults()` sets that to **10 seconds**, and `CaptureCoordinator.preflight` only overrides `maxMessageBytes`. gRPC's graceful shutdown lets pre‑existing calls continue, and the BES bidi stream is open for the whole build, so the wait runs its full budget **on the EDT**, then `shutdownNow()` kills the live stream. Line 199 then interrupts the capture thread, triggering H3. `CaptureCoordinator.close()` is `synchronized` but `run()` is not, so the monitor is free and nothing blocks the tear‑down.

The comment three lines above says "A running build is deliberately not killed here: closing a window is not a request to destroy a capture in progress." That is true of the Bazel *subprocess* (nothing calls `cancel()` or `destroy()`, so the client keeps building) and false of everything else.

**Failure scenario.** User starts `test //...`, capture running, clicks the window's close button. The frame stays on screen, unrepainted, for ~10 s (project rule 8: "Never block the Swing EDT with I/O or computation"; `LaunchController`'s own javadoc: "All of it happens on the supplied worker"). Then the BES stream is killed, Bazel's upload fails and it exits 38, and the capture thread is interrupted mid‑finalization.

**Fix.** Split the two cases in `dispose()`: only call `discardPlan()` for a plan that was never launched; if a build is running, either prompt or stop it through `coordinator.cancel(mode)` and `awaitTermination` with a bounded timeout. Never call `BesServer.close()` from the EDT — hand the close to the capture worker or a dedicated thread. `LaunchController.discardPlan()` should refuse to close a coordinator that is currently running.

**Refutation.** 2 of 9 refuted, and their argument deserves weight because **the same code produced a refuted filing too** (see R16 below): disposing the only window ends the JVM. Every thread in the app is a daemon (`worker`, `captureWorker`, `journalThread`, `storeThread`, `bbv-bes-handler`, the process pumps), `Main` creates exactly one frame with no `WindowListener`, and a measured probe showed the JVM exits ~5–6 s after `dispose()`. So the capture cannot survive the close under any implementation, and without `shutdownNow()` the finally would not run *at all* — the interrupt arguably salvages the SQLite half, since `recordOutcome`/`events.flush()`/`database.close()` go through JNI rather than an interruptible NIO channel.

**What survives that argument:** the ~10 s frozen EDT is caused specifically by line 197 and is not excused by the JVM exiting afterwards; the in‑code comment is false; and the interrupt‑driven finalization converts "staged bytes still in the page cache after a graceful close" into "journal marked failed, staged bytes cleared, `force()` skipped". Two refuters proposed LOW ("a slow, beach‑balling quit"). Treat the EDT block as the certain defect and the data loss as bounded (≤500 ms of journal buffer, plus the missing fsync) — but fix both, because the fix is the same change.

### H5 — A `--bes_backend` set in `.bazelrc` is never detected, so plan 8.5's mandatory conflict is skipped and the team's backend is silently superseded

**Confidence: unanimous, 3‑0.**
**Location:** `InstrumentationPlanner.java:110` (the gate) and `:493‑501` (`UserFlags.of`).

**Defect.** `UserFlags.of` builds its map only from `command.startupArgs()` + `command.commandArgs()` — the argv the user typed. No production code reads rc files, runs `--announce_rc`, or calls `canonicalize-flags` (grep over all main sources finds only comments in `BazelCapabilityDetector`). So `userFlags.has("bes_backend")` is false for an rc‑supplied backend, no `EXISTING_BES_BACKEND` conflict is raised, and `addBesBackend` appends the loopback backend.

**Failure scenario (measured end to end).** A `.bazelrc` containing `build --bes_backend=grpc://127.0.0.1:41111` plus `build --bes_timeout=5s`; `bbv run --json -- build //...` returned `"injectedFlags": ["--bes_backend=grpc://127.0.0.1:56905","--bes_timeout=60s","--build_event_publish_all_actions"]`, captured 36 events into our loopback server, `"warnings": []`, `instrumentation-plan.json` `"replacedFlags": []`, manifest `"warnings": []`. Precedence was independently measured — with `nc -l` on both ports, the command‑line backend received the HTTP/2 preface and the rc backend received **0 bytes** — so the team's backend gets nothing for that invocation, with no conflict, no `ReplacedFlag`, and no record. This is exactly what plan 8.5 and ADR‑007 exist to prevent, and `docs/bazel-ground-truth.md:860` lists rc‑vs‑command‑line precedence as unverified, so the design rests on an interaction the project's own ground truth flags as untested.

Two further reaches from the same root cause, both observed: `addBesTimeout` skipped its "user set their own" guard and injected `--bes_timeout=60s` over the rc's `--bes_timeout=5s`; and `hasNegated` is equally rc‑blind, so an rc `build --nobuild_event_publish_all_actions` is silently re‑enabled with no `ACTION_PUBLICATION_DISABLED` conflict.

Note the team already knows: `RealBazelBesTest.java:150` adds `--nohome_rc` with the comment "keep this run from reading a developer's ~/.bazelrc, which may set --bes_backend itself". The test is defended; the product is not.

**Fix.** Expand the user's effective option set before planning — `bazel canonicalize-flags --for_command=<cmd> -- <argv-options>` is the scriptable oracle the ground truth already identifies (recommendation 3), or parse the rc chain — and feed the result into `UserFlags`. Any `bes_backend` found there must raise the same mandatory conflict, with the detail naming the rc file. If detection cannot be made reliable, the plan must carry a mandatory conflict saying the rc files were not inspected, rather than reporting no conflict.

**Refutation.** 0 of 3 refuted. Strongest challenge: the harm is one‑sided — the user's own capture succeeds, only the upstream backend misses the invocation — so this is a consent/transparency defect rather than data loss, and one refuter argued for MEDIUM. Two rebuttals kept it at HIGH: ADR‑007's stated identity is "never overrides a flag the user set explicitly", and the sibling hazard is worse — rc‑set companions such as `--bes_header=x-buildbuddy-api-key=…` (the standard BuildBuddy onboarding line) are equally invisible and would be sent to the loopback server along with the events. Also noted: if precedence went the other way, the capture would be silently *empty* and `isComplete()` would report 0 == 0 as complete (C4), so both branches are silent failures.

### M1 — `--json` reports `injectedFlags` containing a `pending-raw` path that never existed

**Confidence: unanimous, 3‑0.**
**Location:** `CaptureCoordinator.java:285` (`preflight.plan()` passed into `CaptureResult`), consumed at `RunCommand.java:296`.

**Defect.** `preflight()` plans against `request.sessionsRoot().resolve("pending-raw")` (line 148) because no session exists yet. `run()` correctly re‑plans against `layout.rawDirectory()` (line 211) and uses that plan for the manifest, the plan file, and the launch — then returns `preflight.plan()` in the `CaptureResult`. `CaptureResult`'s own javadoc documents the component as "what was launched and why".

**Fix.** Hoist the re‑planned `InstrumentationPlan` out of the try block (initialise to `ready.plan()`, assign at line 211) and pass it to the `CaptureResult` constructor. Also, `effectiveCommand` appears only in `planJson` (`--dry-run`), not in `resultJson`, so the run‑time symptom is confined to one JSON field. One refuter noted the fix must default to `ready.plan()` because the `SQLException`/`InterruptedException` paths can reach the return before line 211 completes.

### M2 — Exit 38 is reported as "build failed" / `"succeeded": false`, the one code the project documents as unreadable

**Confidence: contested, 5‑1** (CLI lens 3‑0, UI lens 2‑1).
**Location:** `RunCommand.java:222‑227` and `:280`; `MainWindow.java:602‑605`.

**Defect.** Both renderers read `ProcessOutcome.isSuccess()` directly, which is a pure "was the number zero" predicate whose own javadoc says Bazel's exit codes are "recorded but not interpreted here". `CaptureResult.buildOutcomeKnown()` exists for exactly this and has **zero production callers** — only `CaptureResult` itself and one real‑Bazel test. `docs/bazel-compatibility.md`: "Exit code 38 means the upload failed and **masks the build's own result**."

**Failure scenario (reproduced with real Bazel 7.6.1 and an unreachable upstream backend).** `bbv run --keep-bes --quiet -- build --bes_backend=grpc://127.0.0.1:41111 //:t0` printed `state: READY / build: failed, exit 38 / capture: complete`, and `--json` emitted `"succeeded": false`. The session's own `raw/stderr.log` contains `INFO: Build completed successfully, 1 total action` followed by the BES upload error. A successful build is reported as failed, and a script keying on `.build.succeeded` reads a false boolean beside exit code 0 (`exitCodeFor` reports the capture, not the build). `CaptureResult`'s javadoc names this outcome explicitly: "Reporting 'build failed' from that code would blame the user's build for this application's transport problem."

**Fix.** Branch on `result.buildOutcomeKnown()` first: print `build: outcome unknown (bazel exited 38: the event upload failed)`. In `resultJson`, add `"outcomeKnown"` and omit `succeeded` (or emit JSON null) rather than asserting `false`. Do the same in `MainWindow.describe`, and surface `result.warnings()` in the capture panel — `MainWindow.showSessionInfo` currently only does `log.info("session {} carries {} manifest warning(s)", …)`, logging the *count* and not the text.

**Refutation.** 1 of 6 refuted (the UI vote). Their argument: Bazel's own verdict is streamed live into the Console card, the session is finalized INCOMPLETE with a `STREAM_FAILED` diagnostic, and the CLI *does* print the correcting warning ("bazel exited 38 (build event upload failed); the build's own result is not knowable from its exit code") immediately below the wrong line — so nobody is left uninformed. Two things defeat that for the CLI: `warnings` is an unstructured string array while `.build.succeeded` is the typed field a script reads, and the exit code is 0, which lends the wrong field credibility. For the UI it lands harder: `captureFinished` never surfaces `result.warnings()` at all, and exit 38 does not require an incomplete capture — an upload that fails *after* everything was received yields `captureComplete() == true`, so the panel shows the green terminal phase reading "build failed · capture complete · N events indexed".

### M3 — `hasNegated()` recognises only two of Bazel's six false spellings

**Confidence: contested, 2‑1.**
**Location:** `InstrumentationPlanner.java:507‑511`.

**Defect.** `hasNegated` compares the attached value against the literals `"false"` and `"0"`, case‑sensitively. Bazel's `BooleanConverter` accepts `false|f|0|no|n` under `Ascii.toLowerCase`. `valueOf` delegates to `CommandLineParser.attachedValue`, a pure `substring`, with no normalisation.

**Failure scenario (run against the shipped classes).**

```
=no    -> injected=[…, --build_event_publish_all_actions] conflicts=[]
=false -> injected=[…]                                    conflicts=[ACTION_PUBLICATION_DISABLED]
=False -> injected=[…, --build_event_publish_all_actions] conflicts=[]
=0     -> injected=[…]                                    conflicts=[ACTION_PUBLICATION_DISABLED]
=n, =f -> injected=[…, --build_event_publish_all_actions] conflicts=[]
```

A user who writes `--build_event_publish_all_actions=no` to keep the stream small gets the single highest‑overhead flag in the catalog turned back on by last‑wins, with no conflict, no `ReplacedFlag`, and no warning. Separately, the same method ignores ordering: `build --nobuild_event_publish_all_actions --build_event_publish_all_actions //...` (where the user re‑enabled it) reports the conflict anyway and tells them "the session will show which targets built but not which actions ran" — false for the command they gave.

**Fix.** Parse with Bazel's own vocabulary, case‑insensitively: `Set.of("false","f","0","no","n")` and `Set.of("true","t","1","yes","y")`. Have `UserFlags` keep the last occurrence's effective boolean rather than "a `no` key exists". Note that this alone still leaves the override silent for unknown spellings — the safe form is to raise the conflict whenever the flag appears at all and skip injection only when it resolves to true.

**Refutation.** 1 of 3 refuted. Their argument: the override is not silent — `printPlan` and the plan dialog both list the flag as added, with the doubled flag visible in the `effective:` line, and the session manifest records `effectiveCommand` and `injectedFlags` permanently; the measured cost is +44 events / +22–25 KB on a clean 20‑genrule build and ~zero on an incremental rebuild, so the user ends up with *more* data than requested in a session they asked the tool to capture. The blind spot is `bbv run --quiet` without `--json`. The rebuttal: `printPlan` presents the flag as an *addition*, never as contradicting something the user typed, and it is skipped entirely under `--quiet` **or** `--json`; ADR‑007's bullet is unconditional.

### M4 — The manifest records `containsEnvironmentValues=false` on every captured session

**Confidence: contested, 2‑1.**
**Location:** `CaptureCoordinator.java:474‑476`.

**Defect.** The flag is computed solely from `!request.environmentOverrides().isEmpty()`, and `CaptureRequest.of` seeds that map with `Map.of()`. The record exposes `withPreset`, `withConsole`, `withProgress`, `withOptions` and no `withEnvironmentOverrides`; neither `RunCommand` nor `MainWindow` supplies one. The value is therefore `false` for every Phase 2 capture without exception. The comment above the code justifies `containsAbsolutePaths(true)` as "stated rather than assumed absent, so the sensitivity warning is honest"; the environment claim does the opposite.

**Failure scenario.** `bbv run -- build --action_env=NPM_TOKEN=s3cr3t //...`. `writeManifest` stores that argv verbatim in `originalCommand` and `effectiveCommand`, `InstrumentationPlanCodec` writes it again into `instrumentation-plan.json`, and Bazel's `StructuredCommandLine`/`OptionsParsed` events carrying `--client_env=…` pairs go into the raw journal. The manifest nonetheless says `"containsEnvironmentValues": false`. Plan 10.3 requires the manifest to state "whether the session contains absolute paths or environment values" and plan 22.2 makes it the session sensitivity warning; the Phase 1 sibling path (`BepImporter.java:1290`) deliberately leaves the key **absent** — the honest encoding for unknown, per `SessionManifest`'s own doctrine — while the capture path promotes unknown to an affirmative false.

**Refutation.** 1 of 3 refuted. Their strongest argument: the field has **no consumer** — grep finds only the record, the codec, and a round‑trip test; no UI, CLI, or export path reads it. `containsAbsolutePaths` is unconditionally true on every session this tool writes, so any manifest‑driven sensitivity gate already fires 100% of the time; `redactionState` (the field that actually answers shareability) is honestly absent; the token is printed in plaintext three lines above in `originalCommand`; and Phase 9 (export/redaction) is "Not started", with `docs/privacy.md` specifying redaction as unconditional rather than gated on this boolean. The rebuttal: the wrong value is *persisted*, baked into every manifest a future reader will trust, in the artifact `docs/instrumentation-planner.md` says exists to answer questions months later.

Third refuter's summary, which is the fair reading: real, unguarded, fallback‑only, and better rated LOW–MEDIUM.

This is the same change that fixes L5.

**Refutation.** 0 of 3 refuted. Strongest challenge: no data is lost — ADR‑004 keeps the exact bytes in `raw/stdout.log` and `raw/stderr.log`, so the defect is interactional rather than a data defect, and MEDIUM is the ceiling. Two refuters also flagged an adjacent inaccuracy in the same class: the javadoc's claim that "this view rewrites only when the resolved text has actually changed" is unimplemented — there is no comparison anywhere, so even a chunk of pure ANSI cursor movement triggers a full rewrite.

### M8 — Console write failures are swallowed and the manifest still records stdout/stderr as COMPLETE

**Confidence: contested, 2‑1.**
**Location:** `ConsoleCapture.java:90‑100`; consequence at `CaptureCoordinator.java:439‑452`.

**Defect.** `accept` catches `IOException` from `target.write(...)`, logs a warning, and returns — and because `counter.addAndGet(length)` is *inside* the try after the write, the dropped bytes are not even reflected in `stdoutBytes()`. There is no failure flag and no dropped‑byte count. `updateManifestCounts` then records both STDOUT and STDERR with `outcome == null ? UNKNOWN : COMPLETE`, and passes `OptionalLong.empty()` for the size even though `ConsoleCapture` computed it. `stdoutBytes()`/`stderrBytes()` have **zero callers** anywhere in the repository.

**Failure scenario.** A long build runs and the volume holding the session fills (or a network mount drops). Every subsequent chunk on that stream is dropped the same way. The build ends, both sources are recorded `Completeness.COMPLETE` — documented as "Every record the source claims to contain was read intact" — `bbv run` prints no `!` line, and `bbv inspect` prints `source STDOUT COMPLETE`. The user reads a `raw/stderr.log` that stops in the middle of the build with no way to know the rest was thrown away. The same package already has the correct pattern for the sibling case: `CaptureDiagnosticCodes.JOURNAL_WRITE_FAILED`.

**Fix.** Give `ConsoleCapture` a per‑stream failure record (first `IOException` plus a dropped‑byte count) and expose it; have `CaptureCoordinator` pass `Completeness.TRUNCATED` plus a session warning for any stream whose capture reported a failure, and pass the real `stdoutBytes()`/`stderrBytes()` as the source size.

**Refutation.** 1 of 3 refuted. Their argument: a disk full enough to truncate the console log has already broken the journal (terminal and loud — INCOMPLETE plus "the capture failed: …"), SQLite, and the manifest write itself (`AtomicFiles` needs a temp file), so the premise of a confidently‑COMPLETE manifest on a full disk is unreachable; the `log.warn` goes to stderr through logback's root WARN appender; and `downstream.accept` still runs after the failed write, so the bytes still reach the user's terminal and the UI console. They also correctly demoted the second mechanism in the original filing (`BazelProcess.drain()`'s shared deadline with a 1 ms floor): `awaitStreamsToSettle` (5–15 s) and `pipeline.finish()` run before `closeQuietly(console)`, so the pumps get far more wall time than a shared 2 s budget suggests, and per‑stream monitors mean a slow stdout cannot starve stderr. What survives is the non‑disk‑full trigger (read‑only remount, dropped network mount, EIO) and the structural point that a source is stamped COMPLETE from a proxy (`outcome != null`) while the counters that would prove it are dead code.

## LOW

### L1 — The progress reporter tests a throttled counter for exact multiples of 5,000, so it effectively never fires

**Confidence: contested, 2‑1.**
**Location:** `RunCommand.java:330‑339`.

**Defect.** The line prints only when `progress.received() % 5_000 == 0`, but `LiveCapturePipeline.publishProgress` is throttled to one callback per `progressInterval` (250 ms) plus a forced callback per SQLite batch flush, and `received` is a free‑running per‑event `AtomicLong`. At the measured 86,000 events/s the counter advances ~21,500 between callbacks, so the chance any callback lands on a multiple of 5,000 is about 1 in 5,000. The forced publishes also reset `lastProgressMillis`, skipping still more values. No `[bbv]` line appeared in any of six real‑Bazel runs.

**Fix.** Track the last reported count and print when `received() - lastReported >= 5_000`; or simply print on every throttled callback, which is already rate‑limited to ~4/s.

**Refutation.** 1 of 3 refuted. Their argument, which is worth heeding before changing behaviour: the listener is installed only when `!quiet && !json`, which is a strict subset of `!quiet` — i.e. exactly the mode in which Bazel's own console output is already being forwarded to the same stderr. So "no indication that capture is proceeding" is false, and a fixed version emitting up to ~17 lines/s (250 ms throttle plus one per batch flush) would shred Bazel's `\r`-driven progress display, which is what the comment above the line warns about. They also noted the two conditions are anticorrelated: when the counter races, Bazel is printing; when Bazel is quiet, the counter is not advancing. **Prefer deleting the dead modulo, or printing unconditionally on the already‑throttled callback, over "fixing" it to fire often.**

### L2 — `bbv run --help` documents exit code 4 for cancellation, but no cancellation of `bbv run` can produce it

**Confidence: contested, 2‑1.**
**Location:** `RunCommand.java:411‑413`; shared table at `CliMain.java:108`.

**Defect.** `exitCodeFor` returns `ExitCode.CANCELLED` (4) when the session finalizes CANCELLED, but the only thing that can cancel a `bbv run` is the shutdown hook, which runs only when the JVM is already terminating on a signal. A JVM killed by SIGINT exits 130 and by SIGTERM 143 whatever `System.exit` is later handed. Measured: SIGINT 12 s into a slow build produced a correct `"state": "CANCELLED"` session and shell exit **130**. `bbv import --help` carries the caveat verbatim ("the shell reports 130 rather than 4 … Scripts checking for an interrupted import should accept either"); `bbv run --help` does not. `CliMain`'s shared table is additionally wrong for `run`: it describes 4 as "interrupted; the session was left resumable (`bbv import … --resume`)", but a cancelled capture is finalized to `CANCELLED`, a terminal state with an empty `allowedNext()`, and `ImportCommand.locateResumableSession` skips terminal candidates.

**Fix.** Add the 130/143 caveat to `RunCommand.printHelp`, and split the shared table so code 4 reads "interrupted — for `import` the session is resumable, for `run` it is finalized as CANCELLED and inspectable".

**Refutation.** 1 of 3 refuted. Their argument: cancellation is already reported through the primary channel and reliably so — `report(...)` runs *before* `guard.settled()`, and the hook blocks on that latch precisely so the summary reaches the terminal first, printing `state: CANCELLED` and `"terminatedBy":"CANCEL"` in both text and JSON. 130 is the universal SIGINT convention and is non‑zero, so no script reads a cancelled run as success; and the JVM's 128+signal behaviour cannot be changed from a hook. `docs/implementation-status.md:156‑158` already records the fact for the import path. Fair; this is a help‑text accuracy fix, not a behavioural one.

### L3 — `sendInterrupt` signals a bare PID with no liveness check, and the stop controls stay armed for seconds after Bazel has exited

**Confidence: contested, 2‑1.**
**Location:** `BazelLauncher.java:291‑293`; window created by `CaptureCoordinator.java:251` vs `:265`.

**Defect.** `running` stays populated from `running.set(process)` until `run()`'s finally, which is reached only after `await()`, `drain()` (up to 2 s), `awaitStreamsToSettle()` (5 s, or 15 s after a force‑kill) and `pipeline.finish()`. Throughout that window all three UI stop buttons are enabled and the CLI's Ctrl‑C hook is armed. `awaitSignalReadiness` returns early because `!process.isAlive()` — that `isAlive` check **skips the 1 s hold, it does not skip the signal** — and `apply(CANCEL)` then unconditionally runs `/bin/kill -INT <pid>` against a PID the JDK's process reaper has already `waitpid()`'d and released. `java.lang.Process.destroy()` is safe against this because the JDK checks `hasExited` under the process lock; the raw `/bin/kill` path has no such check. Confirmed empirically: after `waitFor()` returns, `Process.pid()` still hands back the stale PID and `ProcessHandle.of(pid).isPresent()` is already false.

Note the codebase defends against PID reuse elsewhere and not here: `SessionLock.java:193‑203` checks `ProcessHandle.of(record.pid())` *and* compares start times.

**Fix.** Return early from `apply`/`sendInterrupt` when `!process.isAlive()`, and clear `running` (or flip the coordinator to a FINISHING phase whose `cancellable` is false) as soon as `process.await()` returns, so the stop controls disarm when there is nothing left to stop.

**Refutation.** 1 of 3 refuted. Their argument: PID recycling inside a 1–15 s window requires the OS PID space to wrap (32 k on default Linux, 99 k on macOS), i.e. thousands of process creations per second immediately after the client exits; without recycling the kill exits 1, is logged ("could not interrupt N; falling back to terminate"), and `destroy()` on a dead process is a no‑op. `awaitStreamsToSettle` also only spins *while BES streams are open*, so on a normal exit the window is short. They further argued the no‑op click is the correct result — marking a self‑completed build CANCELLED would be the actual lie. Accept the downgrade in framing: the defect is "stop controls stay armed after the process is gone, producing a silent no‑op and an unguarded raw signal", and the `isAlive` guard is one line.

### L4 — A startup option given a separate dash‑prefixed value swallows the Bazel command, and the plan then refuses a valid build with a false reason

**Confidence: unanimous, 3‑0.**
**Location:** `CommandLineParser.java:227`.

**Defect.** `BazelCapabilityDetector.toSpec` deliberately drops flags whose only command is `startup`, so no `FlagSpec` can ever satisfy `appliesTo("startup")` — the capability branch is dead for the entire startup segment and every startup flag falls to the heuristic at line 227. For `--host_jvm_args -Xmx4g`, `-Xmx4g` starts with `-` so `isFlag` is true and it is not bound; the next iteration treats `-Xmx4g` as a startup flag whose own heuristic then accepts the following token, so `build` is consumed as its value.

**Failure scenario.** `bbv run -- --host_jvm_args -Xmx4g build //...` (the space form is legal Bazel; the C++ client normalises it). Reproduced against the shipped jars:

```
typed   = [--host_jvm_args, -Xmx4g, build, //...]
startup = [--host_jvm_args, -Xmx4g, build]
command = '//...'   targets = []
canLaunch = false
  conflict COMMAND_NOT_INSTRUMENTABLE: ''//...' does not publish a build event stream'
    -> cancel-and-edit   (the only resolution)
```

A legal command is refused with a nonsensical explanation and no way forward but Cancel. The attached form `--host_jvm_args=-Xmx4g` parses correctly. `docs/bazel-ground-truth.md` §10 item 1 already calls for marking `--output_base`, `--max_idle_secs`, `--host_jvm_args`, `--bazelrc`, `--noblock_for_lock` as startup — the mitigation the design asked for and did not get.

**Fix.** In the startup loop only, stop binding separate values for tokens the capability table does not know: the first non‑flag token after the startup segment is the command by definition. Alternatively keep the startup‑only `FlagSpec`s in a separate map rather than discarding them in `toSpec`, so `--host_jvm_args` is known to require a value.

**Refutation.** 0 of 3 refuted. Corrections accepted: the degenerate case `bazel -- build //...` in the same filing is **not** a defect — the real Bazel client rejects a bare `--` as an unknown startup option, so refusing it is correct and only the message is nonsensical. The trigger is narrow (a startup option given a separate value that itself begins with `-`; `--output_base /tmp/ob` parses fine), the failure is closed (no wrong build, no data loss — the assembled effective argv is actually correct and the tool refuses it on the mislabelled `command` field alone), and it only bites on a successfully probed binary, since an unprobed one takes `isInstrumentable`'s true branch.

### L5 — Every coalesced console repaint rebuilds the whole document

**Confidence: contested, 2‑1.** Same code as M7; one fix serves both.
**Location:** `ConsoleView.java:85‑92`.

**Defect.** Each repaint calls `model.text()` (which allocates a fresh `StringBuilder` and re‑concatenates the entire retained buffer — up to `DEFAULT_MAX_LINES` = 20,000 lines, ~2.2 MB) and `area.setText(...)`, re‑creating ~20,000 leaf elements and re‑measuring the longest line. Measured at the cap: 15.5 ms steady state, 30–50 ms on first passes. `repaintPending` is cleared at the top of the queued runnable, so the next chunk re‑arms immediately. It is also paid unconditionally — including for a chunk of pure ANSI cursor movement that changed `model.text()` not at all, which the class javadoc claims is avoided.

**Fix.** Append the delta via `Document.insertString` instead of rewriting; if a full rewrite is kept, skip it when the resolved text is unchanged (cheap: compare committed‑line count plus partial‑line length).

**Refutation.** 1 of 3 refuted. Their argument, and it is a good one: the cited 33 ms budget belongs to `docs/performance.md` objective 5 (timeline/graph panning), not to a console. The objectives that govern this code are #4 ("live UI updates at least four times per second" — 250 ms, cleared 16×) and #10 ("no routine EDT pause exceeds 100 ms" — cleared 6.5× at steady state). They then measured the thing the claim is actually about: with a chunk every 10 ms at the retention cap, input‑event latency behind the console loop was **mean 10.0 ms, worst 37.7 ms** — because `repaintPending` caps outstanding rewrites at one, so the repaint rate self‑limits as it gets more expensive. Nothing is stale (`text()` recomputes, so a late repaint shows newer content), nothing is lost. Treat this as a cleanup you get for free when fixing M7, not as a performance defect on its own.

## REFUTED candidates

These are as useful as the confirmed findings: each is a place where a reviewer's intuition about this code was wrong, and the reason is worth internalising before filing a similar report.

**Concurrency / BES protocol**

1. **`close()` interrupts the store thread without joining, then the coordinator uses the same `EventWriter`** (`LiveCapturePipeline.java:517`, 2 of 3) — `finish()` joins both threads *before* anything that can throw `IOException`/`SQLException`, so `close()` only ever interrupts dead threads except on the interrupted‑caller path, where `summary` is null and no manifest count or completeness claim is produced at all.
2. **Store thread reads `JournalWriter`'s unsynchronised fields when checkpointing** (`LiveCapturePipeline.java:322` and `:565`, filed twice, 3 of 3 both times) — nothing ever reads a live‑capture `import.ckpt` (`BepImporter.resume` throws first on the missing `import-source.json` sidecar, which capture never writes), both readers bounds‑check an ahead position and fall back to a full rescan, and `finish()` rewrites the checkpoint single‑threaded after joining.
3. **A refused submit leaves the sequence in `inFlight`, so a retry acks an unjournaled event** (`PublishBuildEventService.java:311`, 3 of 3) — `CaptureRejectedException` is terminal (`accepting` never returns to true, `failure` is never cleared), so no later event on that stream is journaled either; the retry's next new sequence fails the RPC with UNAVAILABLE and the session is reported INCOMPLETE.
4. **Acks are written to the submitting connection, not the one owed them, producing an out‑of‑order ack that kills the Bazel server** (`PublishBuildEventService.java:326`, 2 of 3) — one bounded FIFO queue with one journal thread makes callback order equal enqueue order; under backpressure AQS hands the freed slot to the first‑parked producer, so the inversion the repro imposed with an unbounded `LinkedBlockingQueue` cannot arise, and the misrouted range is redundant because the DUPLICATE branch already acked those sequences on the live connection.
5. **A duplicate sequence is acked before, or without, being journaled** (`PublishBuildEventService.java:275`, 2 of 3) — the immediate DUPLICATE ack is contract‑mandated and load‑bearing: the dead connection's `onJournaled` callbacks go to a dead observer and are swallowed, so the replay learns of in‑flight sequences *only* this way; removing it produces the "not all ACKs received" hang the design exists to avoid.
6. **A stream that finishes cleanly on a retry connection can be recorded ABORTED** (`PublishBuildEventService.java:456`, 2 of 3) — Bazel's uploader tears down the failed stream and backs off ~1 s before opening the replacement, while the server records the cancel in microseconds, so two connections for one `StreamId` are never concurrent; and the error direction is "looks incomplete but is complete", the safe one.
7. **The header wire walk disagrees with `parseFrom` on a repeated singular message field** (`BesRequestHeader.java:83`, 3 of 3) — `BesRequestHeader` is the only producer of `BesStreamKey` in the whole tree; `BesEnvelopeDecoder`'s identity fields feed one display header in the raw‑payload inspector, so the two decoders' answers are never compared, and per‑call identity is frozen by the first request.

**Process launch**

8. **The 1 s signal hold is bypassed for `bbv run` because the client shares the process group** (`BazelLauncher.java:253`, 2 of 3) — the PGID observation is correct, but the same tty SIGINT starts `CancellationGuard`, which blocks JVM exit for up to 30 s and delivers bbv's own held SIGINT at client age ≥ 1 s; measured, a child that ignores the first signal is stopped by the held one at t≈1010 ms. Isolating the client into its own process group is the option `docs/bazel-ground-truth.md` §6.1 explicitly declined.
9. **Shell mode joins argv with single spaces into `sh -c`** (`BazelLauncher.java:96`, filed twice, 3 of 3 both times) — `shellMode` is hard‑`false` at every construction site (`CaptureRequest.of` passes `false`, there is no wither, no CLI flag, no UI control, no test), and unquoted joining is the *specified* semantics of a feature whose stated purpose is shell expansion, wrappers, pipes and substitutions.
10. **`sendInterrupt`'s SIGTERM fallback still records `CancellationMode.CANCEL`** (`BazelLauncher.java:291`, 2 of 3) — `terminatedBy` is a ladder rung (the stop the user asked for), not a signal name; no consumer branches on CANCEL vs TERMINATE except the FORCE_KILL settle budget, and the ladder overwrites it with the harsher rung whenever the fallback fails to stop the client.
11. **Concurrent cancels race on `cancelledWith`** (`BazelLauncher.java:206`, 2 of 3) — `await()` reads the field once, milliseconds after the process dies (`drain()` returns at pipe EOF, not at its 2 s deadline), and everything downstream consumes the immutable `ProcessOutcome`; a click seconds later writes a field nobody reads again, and every other interleaving writes monotonically harsher.

**Planner**

12. **`run()` re‑plans with an empty veto set** (`CaptureCoordinator.java:217`, filed twice — 2 of 3 by the planner lens, 3 of 3 by the session lens) — no shipped surface can produce a veto: `PlanRequest.vetoing` has exactly one caller (a planner unit test), `LaunchController.replan(UnaryOperator)` has **zero** callers, and `InstrumentationPlanDialog.Choice` is `{LAUNCH, CANCEL, RESOLVE}` with flags rendered as read‑only text. Latent trap, not a live defect. *(The session filing's second half — `CaptureResult` returning the stale plan — survives separately as M1.)*
13. **An unrecognised conflict‑resolution id clears the mandatory conflict and replaces the backend with no `ReplacedFlag`** (`InstrumentationPlanner.java:119`, 3 of 3) — both production callers derive the id from the conflict's own resolution list (the dialog assigns `resolvedKind` and `resolutionId` in the same button closure), so a foreign id can never be paired with `EXISTING_BES_BACKEND`; the CLI maps two booleans to named constants.
14. **`UserFlags.raw()` returns only the flag token for a space‑separated value, so the conflict never names the backend** (`InstrumentationPlanner.java:513`, 2 of 3) — the dialog and `printPlan` both display the full original and effective argv immediately above the conflict text, and `originalCommand`/`effectiveCommand` in the manifest and plan JSON preserve the URL; only the `ReplacedFlag.original` string and `offendingArgv` (which has no UI or CLI reader) are truncated.
15. **A vetoed flag is reported with `capabilityStatus = UNSUPPORTED`, stating a falsehood about the user's Bazel** (`InstrumentationPlanner.java:252`, 2 of 3) — unreachable for the same reason as 12: nothing vetoes `BES_TIMEOUT` anywhere, and `run()` re‑plans with an empty veto set regardless.

**Session / UI**

16. **Closing the window interrupts finalization, truncating the journal and leaving the manifest stuck in CAPTURING** (`MainWindow.java:199`, 2 of 3) — disposing the only window ends the JVM (every thread is a daemon; measured ~5–6 s), so without the interrupt the finally would not run at all and the same staged bytes would be lost plus the SQLite batch; a `CAPTURING` manifest is a designed, tested, recoverable state, and `AtomicFiles` leaves the previous manifest byte‑identical on a failed write. **Note the tension:** the same code path survived as H4 from three other lenses. The honest synthesis is that the EDT block and the false comment are real, and the data‑loss framing is the part that does not hold.
17. **stdout/stderr recorded COMPLETE after a force‑kill or a failed console write** (`CaptureCoordinator.java:444`, 2 of 3) — `outcome != null` provably means `process.waitFor()` returned, i.e. the pipes reached EOF and both pumps exited; the ~2.5 s of continued server work after a SIGKILL is a *BES stream* phenomenon, not output on the dead client's pipe, so the post‑kill bytes do not exist rather than being lost. *(The swallowed‑write half survives separately as M8.)*
18. **`LaunchController.replan` runs plan construction on the EDT and leaks the coordinator on failure** (`LaunchController.java:119`, 3 of 3) — the method has zero callers anywhere, and `preflight()` is memoized so the `IOException` branch it fails to `discard()` on is unreachable even if it were called.
19. **Phase 2 writes session files named by modules other than `session-format`, and two are missing from the documented layout** (`docs/session-format.md:10`, 3 of 3) — the two console‑log name constants are cross‑pinned by a passing real‑Bazel test that writes via one and reads via the other; `CaptureSourceEntry.path` is display‑only text that nothing resolves against a session root; and both files are documented in the pages that own them.
20. **stdout and stderr merged into one `ConsoleModel`, so a stderr progress repaint erases stdout lines** (`MainWindow.java:572`, 3 of 3) — the app never gives Bazel a TTY (plain `ProcessBuilder` pipes, no `--curses`/`--color` anywhere), so `\r` and ESC never arrive; measured against real Bazel 7.6.1, zero stdout lines missing and zero glued lines across repeated runs, and even under forced `--curses=yes` the `\r` always lands right after a newline when `current` is already empty. Merging is also the specified rendering (`ConsoleSink`: "rendering is the console view's problem, where the terminal semantics belong").
21. **The plan dialog omits "capture source enabled" and the probe‑failure reason, and offers no disable control** (`InstrumentationPlanDialog.java:152`, 2 of 3) — the dialog never *claims* a flag is disableable (it renders text only in the negative case), the preset combo including `CUSTOM` is a working way to drop the high‑overhead flag, and the probe passes `--ignore_all_rc_files` from a temp dir so the `.bazelrc` scenario cannot occur. *(The missing veto affordance survives as an unrefuted completeness‑critic finding, CC6.)*
22. **`--json` drops every plan warning and unapplied flag** (`RunCommand.java:109`, 2 of 3) — `instrumentation-plan.json` is written to the session unconditionally with `addedFlags` (per‑flag `applied` and `capabilityStatus`), `conflicts`, `warnings`, `errors`, `probeWarnings` and a per‑`DataSource` `sourceAvailability` map, and the JSON's first key is the session path; blockers print to stderr regardless of `--json`, and `planJson` is only ever emitted with `canLaunch: true` because `reportBlockers` returns USAGE first.

**Security**

23. **The embedded BES server authenticates nothing and the plan‑9.1 capture token is generated then discarded** (`BesEndpoint.java:25`, 3 of 3) — plan 9.1's last bullet reads "Generate a unique capture token **internally even if the Bazel endpoint cannot transmit it**; use invocation and stream IDs for correlation", which is what the code does; a `--bes_header` token would land in the process argv (readable by the postulated local attacker), in `session.json`'s `effectiveCommand`, in `instrumentation-plan.json`, and in the ADR‑007 plan dialog. Also, the pipeline is not attached during preflight, so events arriving before `run()` are refused. *Residual worth fixing:* the javadoc's claim that the token lets "a session prove which listener it belonged to" describes a capability that does not exist, since it is never persisted.
24. **`BesStreamKey.storageKey()` collision silently drops a journaled, acknowledged event** (`BesStreamKey.java:41`, 3 of 3) — `componentName()` is slash‑free in every branch, so the trailing segment splits unambiguously, and `build_id` is constant across every stream in one session; a collision requires two forged streams, which means an attacker can only suppress one of its own fabricated events on a socket where it can already inject unlimited ones.
25. **The BES handler executor is unbounded, so a local peer can force unbounded thread allocation** (`BesServer.java:55`, 2 of 3) — the claimed chain does not exist: `OutOfMemoryError` is an `Error` and is caught by neither pipeline thread's `catch (… | RuntimeException)`, so `fail()` is never reached; thread stacks are native and committed lazily, not heap; and the precondition (a hostile local process) already permits fabricating events, rewriting `.bazelrc`, or exhausting the thread table directly. `maxConcurrentCallsPerConnection` would not help either, since there is no connection cap.

## Completeness critic

These ten were filed by a separate pass whose job was to audit what no lens owned — the Phase 2 diff enumerated from git (111 files, 11 commits), build files, lockfiles, vendored protos, benchmarks, test‑support, docs, and the coordinator seam between lenses. **They did not go through the refutation gauntlet**, so they carry no vote tally; several were independently corroborated by measured runs, which is noted below.

**CC1 — CRITICAL — A capture that received zero events is finalized READY and reported "complete"** — `CaptureSummary.java:54`. *Same defect as C4, independently found and measured on three additional triggers* (bad user flag, bad `~/.bazelrc` line, `--keep-bes`), with the manifest observed as `sources: [{"kind":"BES_STREAM","byteSize":0,"completeness":"COMPLETE","note":"0 stream(s), 0 event(s) received"}]` and exit 0. This critic notes what the lenses did not: `docs/implementation-status.md:246` offers `isComplete()` as the evidence for Phase 2 exit criterion 3, so the criterion rests on a predicate that cannot fail for a capture that got nothing. Fold into C4.

**CC2 — CRITICAL — The `KEEP_BES_USE_FILE` resolution writes `raw/bep-fallback.bin` and nothing ever reads it** — `InstrumentationPlanner.java:275`. Verified end to end: Bazel wrote 32,933 bytes of real BEP into the session; `eventCount: 0`; journal 32 bytes; **no manifest source entry for the file at all**; `state: READY`, `complete: true`, exit 0. `grep` for `FALLBACK_BEP_FILE`/`bep-fallback`/`BepImporter` across `capture-bes`, `bazel-runner`, `app` and `ui-swing` main sources returns only the constant, the flag construction, and one planner test. `capture-bes/build.gradle.kts` justifies its dependency on `capture-file` with "the binary-file fallback for a BES conflict (plan 8.5) is its growing-file tail reader" — an edge declared and never used. The user is told, in the dialog and in the plan text, "Your backend still receives everything. This application reads a local copy instead." It never reads it. `docs/phase2-contracts.md` §10 does not list this omission and `docs/implementation-status.md:229` marks it "Done".
**Fix:** either import the file after the process exits (record it as a manifest capture source with size, hash and completeness, and count its events), or remove `RESOLUTION_KEEP_BES_USE_FILE` and `--keep-bes` and record the omission in §10. What must not stand is offering the resolution, writing the file, and reporting the empty session as complete.

**CC3 — HIGH — A `--bes_backend` in a `.bazelrc` is silently overridden with no conflict, no `ReplacedFlag` and no warning** — `InstrumentationPlanner.java:493`. *Same defect as H5*, independently measured. Adds: `docs/implementation-status.md:249` marks exit criterion 6 Met on the strength of a command‑line‑only test, and `docs/bazel-ground-truth.md:860` records that rc‑vs‑command‑line precedence was never tested.

**CC4 — MEDIUM — `CaptureResult.plan()` returns the stale preflight plan** — `CaptureCoordinator.java:285`. *Same defect as M1*, with an extra observed symptom: `--dry-run --json` prints an `effectiveCommand` naming `/tmp/bbvsessions/pending-raw/bep-fallback.bin`, a directory that is never created, in the command the dialog deliberately makes selectable "because the effective command is something people copy into a terminal".

**CC5 — MEDIUM — `run()` discards user vetoes and re‑derives conflict resolutions from the plan's output** — `CaptureCoordinator.java:217`. **Note the conflict:** this is the same claim two refutation panels rejected as unreachable (R12), on the grounds that no shipped surface can produce a veto. The critic's framing is the useful one: `resolutionsOf` exists solely to reverse‑engineer information the coordinator threw away, and it can only recover a resolution whose `AddedFlag` was actually applied. **Fix regardless, cheaply:** store the approved `PlanRequest` on `Preflight` and re‑plan by copying it with only `sessionRawDirectory` and `allowOverwrite` changed. That also deletes `resolutionsOf`/`PlanConflictKinds`, and it is the same change M1 needs.

**CC6 — MEDIUM — ADR‑007's "the user can veto any added flag" is claimed implemented but no affordance exists** — `InstrumentationPlanDialog.java:152`. `addedFlagRow` returns a read‑only `JTextArea`; the only controls are Launch, Cancel and conflict resolutions. `RunCommand`'s option set has no veto flag. `AddedFlag.userCanDisable()` is read only to print "Required: without it there is no capture" when it is *false*. `docs/instrumentation-planner.md:6` lists veto among the rules "the code enforces rather than documents" and says "Implemented in Phase 2"; §10 does not list the omission; `docs/implementation-status.md:230` marks the plan dialog Done.
**Fix:** add the checkbox and wire it to `LaunchController.replan(r -> r.vetoing(cap))` (after CC5), or state the omission in §10 and stop the docs claiming it.

**CC7 — MEDIUM — `docs/performance.md`'s "Accepted (wire to receive queue)" column measures the benchmark client's send loop, not the capture path** — `BesThroughputSpike.java:236`. `report()` computes `summary.received() / sendSeconds`, dividing a *server* count by a *client* duration over two different intervals. Measured: "accepted: 50,000 events in 0.09s = 553,170 events/sec" alongside "acknowledged: 50,000 events in 0.98s = 51,048 events/sec". The server cannot have accepted 50,000 by t=0.09 s — the handler requests at most `FLOW_CONTROL_WINDOW` = 64 ahead and the receive queue holds 4,096, so at most ~4,160 had arrived. The number falls with payload size (1.32M at 0 bytes, 869 k at 512) exactly as a serialization cost would. A reader of `docs/performance.md:400‑405` concludes the receive path does 869 k–1.3 M events/s and only the journal and indexer bring it to ~86 k/s; neither is true.
**Fix:** drop the column, or measure the server side; if the intent is client enqueue throughput, label it and stop dividing by `summary.received()`.

**CC8 — LOW — `BesThroughputSpike` prints no PASS/FAIL and always exits 0** — `BesThroughputSpike.java:253`. It ends with a `println` naming the 100,000 events/s objective and returns normally, at a measured 51,048 events/s. `README.md:75` says "Every spike prints a PASS/FAIL verdict against its budget", it is registered in the same `spikeMains` map, and the other four (`SqlPagingSpike`, `TableSpike`, `TimelineSpike`, `GraphSpike`) all print a verdict and exit non‑zero, two under the comment "Shared spike contract: a budget breach is a nonzero exit". This is the same failure the Phase 0 audit fixed for two of four earlier spikes.
**Fix:** compute the acknowledged rate against a named constant, print PASS/FAIL, `System.exit(pass ? 0 : 1)`, and fail on `!summary.isComplete()` or a received‑count mismatch (today only a MISMATCH line).

**CC9 — MEDIUM — `BazelWorkspaceFixture`'s empty `.bazelrc` does not stop tests inheriting `~/.bazelrc`** — `BazelWorkspaceFixture.java:107`. The comment says it "keeps a test run from inheriting the developer's ~/.bazelrc, which can set --bes_backend, --config or a remote cache and turn a hermetic test into a measurement of someone's laptop". A workspace rc does not suppress the home rc; only `--nohome_rc` / `--bazelrc=/dev/null` / `--ignore_all_rc_files` does. Demonstrated: with `HOME=/tmp/fakehome` containing `common --bogus_flag_xyz=1`, the build printed `Reading rc options … Inherited 'common' options: --bogus_flag_xyz=1` then `ERROR: Unrecognized option`. `RealBazelBesTest` adds `--nohome_rc` at line 150 for exactly this reason; `RealBazelCaptureTest` and `RealBazelCapabilityTest` — which carry the Phase 2 exit‑criteria evidence — do not.
**Fix:** have the fixture expose the startup options a hermetic launch needs, route every real‑Bazel test through one helper that adds them, and correct the comment.

**CC10 — LOW — `BazelBinary` silently reports "no Bazel" when `BBV_TEST_BAZEL` points at a non‑executable path** — `BazelBinary.java:46`. An explicitly configured but unusable override collapses into the same `Optional.empty()` as "this machine has none", never falls through to the PATH search, and `whyUnavailable()` is a constant string telling the operator to "set BBV_TEST_BAZEL to an executable" — which they already did. Every `assumeTrue` then skips, and `./gradlew check` is green with the entire real‑Bazel suite unrun. Since `docs/implementation-status.md:237‑240` rests every Phase 2 exit criterion on those tests, a configuration typo hides exactly the evidence the phase claims. The class javadoc states the opposite intent.
**Fix:** throw (or return a distinguishable failure) when the override is set but unusable, and make `whyUnavailable()` name the rejected path.

## Areas checked and sound

Condensed from the per‑lens and completeness sweeps. These were examined and found correct; several were verified by execution rather than reading.

**BES protocol.** Half‑close/`completeIfDrained` handshake (volatile `halfClosed` + `AtomicLong outstanding`, double‑checked from both sides, incremented before `submit`; gRPC serialises the callbacks, so the close is never interleaved inside `journal()`). Acks never pass a gap — `BesStreamTracker` is fully synchronized, `journaled()` returns `[highestAcknowledged+1, highestContiguous]` and returns empty while `journaledAhead` holds a hole; the `highestAcknowledged ≤ highestContiguous ≤ highestReceived` invariant is enforced by the state constructor. Duplicate/replay across connections (strict‑prefix, partial‑overlap and full‑replay all drove correct ack echoes with each sequence journaled exactly once); a skip‑ahead replay journals but correctly acknowledges nothing. Ack values are never coalesced (one response per sequence, deliberate) and are `long` end to end. Byte fidelity socket→journal is exact — 20 requests from 1 byte to 200 KB, gzip on the wire, journaled payloads byte‑identical. Differential fuzz of the header walk against full `parseFrom` over 22 hand‑built encodings (unknown fields of every wire type, packed repeated, zero‑length submessages, reversed field order, unknown enum numbers, negative sequences, truncated and invalid‑UTF‑8) agreed everywhere except the repeated‑singular case, which is refuted item 7. Field numbers verified against the vendored protos. Stream identity is collision‑free for real Bazel (the `unknown-invocation` placeholder only ever fills the build‑level lifecycle slot). Out‑of‑order buffering is bounded at 1,024 with `TOO_FAR_AHEAD`.

**Pipeline, journal, storage.** FIFO sentinel ordering; the narrow post‑sentinel `submit` race is caught by the re‑check at line 198 and surfaces as `received != journaled` rather than a silent drop. Ack‑after‑append ordering matches contract §3 — a full normalize queue delays no acknowledgement, and nothing is acked before its frame reached the writer. `SettableRawEventSink` CAS attach / refuse‑when‑detached. `BesServer.close()` ordering and idempotence. Message‑size limits derive from one value (`maxMessageBytes` threads into gRPC's inbound limit, `RawBytesMarshaller`, `JournalWriterConfig`, `EventNormalizer`), so nothing the server accepts can be refused by the journal; `RawBytesMarshaller` checks twice, `JournalWriter.append` rejects an oversize payload and an out‑of‑range `streamOrdinal` loudly. `BesEnvelopeDecoder` bounds parsing twice and turns an undecodable envelope into a FAILED row with its raw location. `ImportCheckpointStore`'s temp→force→ATOMIC_MOVE with a `.previous` fallback; a checkpoint failure is non‑fatal. `JournalFormat.SourceKind` was appended (BES_LIFECYCLE=3), not renumbered. `EventNormalizer`'s move to `capture.normalize` is a pure relocation plus the BES branches.

**Process launch.** Buffer handoff is safe on every path — the only sink crossing a thread boundary copies first, and each pump owns its 8 KiB array. A dead pump closes the pipe's read end (EPIPE) rather than stalling the child. `SIGNAL_READY_MILLIS` = 1 s matches ground truth §6.5 exactly and returns early when the process is gone. Force‑kill deliberately does not reap the Bazel server (it is a sibling at PPID 1, as §7 requires) and bazelisk's exec keeps the handle valid. `ProcessOutcome` never fabricates an exit code; `Subprocess`'s `-1` timeout sentinel is contained behind `timedOut`/`isSuccess()` and never displayed. Probe stdout and stderr are drained on separate threads and never merged, and an empty stdout is refused even on exit 0. Environment policy does what each enum promises and records the policy, not values. The cancellation ladder's grace periods are far above the ~25 ms the client actually takes. `ConsoleCapture` writes raw bytes per stream with no decoding, splitting or ANSI stripping.

**Planner and parser.** Injected flags always land in `commandArgs`, after the command and before both targets and any user `--`; verified across nested `--`, negative patterns after `--`, a bare trailing `--`, and an empty target list. No catalog entry uses `Placement.STARTUP`, so the ban on restarting the user's server holds. Nothing whose capability status is not SUPPORTED reaches the argv. `canLaunch()`'s three gates work for every conflict actually raised, and a mandatory conflict cannot be constructed without a resolution. `CommandLineParser` splits real command lines correctly across startup/command partition, interleaved flags and targets, `--config=x`, attached values containing `=`, separate values bound from capabilities, a valueless flag not swallowing a target, and a dash‑prefixed value not misread as a target. flags‑as‑proto degrades safely on every hostile input traced (non‑zero exit, empty stdout, non‑base64, non‑FlagCollection, empty table) and never reports an empty table as success; proto2 absent‑vs‑empty is read via `hasX()` so Bazel 6.5's missing `requires_value` stays `Optional.empty()`; `{"startup"}`‑only flags are dropped; `commands` is membership‑tested, not diffed. **Nothing anywhere gates behaviour on a version number.**

**Session and state.** Legal transitions on the happy path (BFS verified against the compiled enum). The `CAPTURING` transition sits after `BesServer.start()` and before `BazelLauncher.start()`, with the pipeline started and attached first. Events arriving before attach are refused, not dropped. The lock is released on every non‑hanging path, including when `finalizeSession` throws. Close ordering is pipeline → console → journal → events → streams → database, null‑safe throughout. A killed capture leaves a recoverable session (atomic manifest writes, non‑terminal state, stale lock breakable). Two captures can share a sessions root. `InstrumentationPlanCodec` is atomic and genuinely write‑only. `ManagedSession.updateManifest` refuses a state change, so the state field has one writer. A re‑opened session reads back exactly the committed rows. `bbv import --resume` cannot auto‑attach to a captured session. `CancellationGuard` never interrupts the command thread.

**Security.** Loopback binding is enforced at the only bind site and no non‑loopback `BesEndpoint` is constructible; a repo‑wide grep for `0.0.0.0`, `ServerSocket`, `new Socket(`, `openConnection`, `HttpClient` returns that one line. No HTTP server, no outbound connection. The header parse loops terminate on any input (every iteration consumes a tag; `pushLimit` rejects an overrunning length), so a forged request yields INVALID_ARGUMENT rather than a hang. Nothing from an imported or captured session is ever executed — `bazel-runner` imports nothing from `session-format`, and `MainWindow` builds its command from the user's text field. Command arguments are recorded where the plan says and nowhere unexpected; environment *values* are written nowhere. No SQL is concatenated from wire data. The probe runs only the resolved binary with fixed arguments from a fresh 0700 temp dir and is `destroyForcibly()`d on hang.

**UI threading.** `LaunchController`'s hop discipline is correct on every reachable path — preflight, resolve and launch all do the blocking work on the worker and post through `toUi`; console bytes are copied before the hop. Stop buttons hand off without blocking the EDT. Progress delivery ordering is right (the final counters land before `captureFinished`). The Run button is re‑enabled on every path and the BES port is released on the plan‑abandonment and error paths. A second capture is blocked by `isBusy()` plus a CAS. The console line cap *is* disclosed via `droppedLines()` with a pointer to `raw/`. ANSI and carriage‑return handling is correct for a single stream, including escapes split across chunk boundaries. The `EXISTING_BES_BACKEND` conflict wiring is complete: all three plan‑8.5 resolutions rendered with consequences, Launch disabled and not the default while `canLaunch()` is false. Status counters are honest — three separate numbers, an indeterminate bar, "no events yet" instead of zero, an explicit lag flag, `UNKNOWN` rather than 0. Sessions are opened off the EDT after every outcome including CANCELLED and INCOMPLETE.

**CLI.** Stream discipline measured over six real invocations: stdout carried exactly one thing every time, with no log, progress, plan, gRPC or logback output ever reaching it (`logback.xml` pins the appender to stderr with a `NopStatusListener`). Bazel's console goes to stderr as raw bytes, so `\r` progress repaints survive. `--` handling is correct including a nested `--` (instrumentation spliced *before* it — the rule `docs/bazel-compatibility.md` says is fatal to get wrong), a missing `--`, and a stray `--keep_going` refused rather than absorbed. Every argument error returns USAGE and creates nothing. The BES‑conflict refusal prints all three resolutions and creates no session. `--quiet` still writes `raw/stderr.log`. A failing build with a complete stream exits 0 by documented design. Ctrl‑C *during the build* works end to end (CANCELLED, exit 8, 44‑event journal, full summary printed before the JVM dies). The shutdown hook is installed and removed exactly once. No usage error prints a stack trace, and no error path writes to stdout.

**Build and scope hygiene.** Phase 2 enumerated from `git diff` (111 files, 11 commits) and diffed against the eight lens scopes. `.gitignore` is still correctly anchored and every source file is tracked (`find` vs `git ls-files` reports no difference). The vendored `bazel_flags.proto` is genuine, complete for the fields the detector reads, import‑free, and added to both `PROTO_SOURCES.md` and `update-protos.sh`. Build files and lockfiles are consistent — every new dependency edge corresponds to a real import, and `lockAllConfigurations()` still applies. `ManagedSessionLayout`'s additions are purely additive. The CI workflow is unchanged with no test‑tag exclusion. `RawPayloadRenderer`'s BES path distinguishes "carries no build event" from "could not be read" and bounds its own size limit. The throughput spike drives the real path end to end with a `--transport-only` control and cleans up its temp tree. `BazelWorkspaceFixture` generates rather than checks in its workspace, writes both `WORKSPACE` and `MODULE.bazel`, and downloads nothing.

**Latent hazards noted but deliberately not filed** (each currently unreachable or consequence‑free; each becomes a defect the moment the surrounding code changes): the pump thread's `catch (RuntimeException)` sits outside its read loop, so one throwing sink ends that pump permanently — contrary to the comment above it; `BesStreamTracker.reopen()` does not clear `inFlight`; the `DESTINATION_EXISTS` conflict's "overwrite" resolution is offered but keys off `allowOverwrite`, which `resolving()` never sets, so choosing it would loop forever (unreachable today only because preflight plans against a `pending-raw` directory nothing creates); `applyTo()` filters on `Placement` while `appliedFlags()`/`injectedArgv()` do not, so a future STARTUP entry would be reported in the manifest without appearing in the argv; the parser heuristic swallowing a relative target corrupts `BazelCommand.targets()`, which only tests read today but plan 8.6's aquery extraction will not; `BesEndpoint.loopback` hard‑codes `127.0.0.1` while the bind uses `InetAddress.getLoopbackAddress()`, which returns `::1` under `-Djava.net.preferIPv6Addresses=true`; `isLoopback` short‑circuits on the literal string `"localhost"` without resolving it; and there is a sub‑frame window after `launch()`'s `discard(coordinator)` in which `isBusy()` is already false while the EDT has not yet delivered `captureFinished`.
